# Анализ проекта `sfera_kanban`

## Назначение
Проект — это небольшое Flask-приложение, которое получает задачи из внутреннего API Sfera, нормализует данные и показывает их в формате Kanban-доски с двумя режимами группировки:
- по исполнителям;
- по системам.

Пользователь может получить задачи:
1. по метке (например, `23.06-27.06.2025`);
2. по диапазону дат (`start_date` / `end_date`).

## Поток данных (end-to-end)
1. Пользователь открывает `/` и видит форму выбора режима (`templates/query.html`).
2. Форма отправляет POST на `/fetch-tasks`.
3. В зависимости от режима вызывается:
   - `generate_tasks_label(label)`;
   - или `generate_tasks_dates(start_date, end_date, label)`.
4. Функции из `utils/sfera_api.py`:
   - логинятся в Sfera (`/api/auth/login`), получают bearer token;
   - определяют количество страниц результата;
   - постранично читают задачи;
   - приводят поля к внутреннему формату `dict`;
   - сохраняют дамп в `tasks_dict.pickle`.
5. После этого `/kanban`:
   - группирует задачи по исполнителю и по системе;
   - сортирует группы в кастомном порядке;
   - рендерит `templates/kanban.html`.

## Главный модуль `app.py`
### Глобальное состояние
Используются глобальные переменные:
- `tasks` — текущий список задач;
- `label_to_match` — метка, которой подсвечиваются карточки.

Это упрощает MVP, но важно понимать: состояние общее для всех запросов и пользователей процесса.

### Маршруты
- `GET /` → страница формы (`query.html`).
- `POST /fetch-tasks`:
  - `mode=dates`: строится label через `generate_label()` и вызывается `generate_tasks_dates()`;
  - иначе вызывается `generate_tasks_label()`;
  - после загрузки — redirect на `/kanban`.
- `GET /kanban`:
  - `group_tasks_by_assignee(tasks)`;
  - `group_tasks_by_system(tasks)`;
  - сортировка групп `sort_assignees()` / `sort_systems()`;
  - отрисовка шаблона.

### Логика сортировок
- `sort_assignees()` фиксирует приоритетный список ФИО; неизвестные исполнители уходят в конец.
- `sort_systems()` аналогично фиксирует порядок систем; прочие — в конец.

## Интеграция с Sfera (`utils/sfera_api.py`)
### Конфигурация и запросы
- База: `https://tasks.example.local`.
- Авторизация: `POST /api/auth/login`.
- Чтение задач: `GET /app/tasks/api/v1/entity-views`.
- Проверка SSL выключена (`verify=False`), предупреждения urllib3 подавлены.

### Формирование запросов
- По метке: `area = AREA1 and label = '<query>'`.
- По датам: `area = AREA1 and dueDate <= end and dueDate >= start`.

### Нормализация карточек
Для каждой задачи формируется словарь:
- `number`, `name`, `status`;
- `description` (или `' '`);
- `assignee` (или `'Без исполнителя'`);
- `systems` (список имен или `'Без системы'`);
- `date` (`dueDate` или `'Без срока исполнения'`);
- `estimation` в часах (`секунды / 3600`, по умолчанию 0);
- `relation` (`relations` для label-режима и `parent` для date-режима);
- `label` (список меток).

### Побочные эффекты
После формирования список сериализуется в `tasks_dict.pickle`.

## Утилиты группировки (`utils/task_utils.py`)
- `sort_tasks()` сортирует внутри колонки по бизнес-приоритету статусов.
- `group_tasks_by_assignee()` делает `dict[assignee] -> list[task]` + сортировка задач.
- `group_tasks_by_system()` раскладывает одну задачу по всем системам из `task['systems']`; если поле строка, приводит к списку.

## UI: страница запроса (`templates/query.html`)
- Два radio-режима: `label` и `dates`.
- Для label используется `datalist` с автоматически сгенерированными неделями (текущая неделя ±10).
- Для dates показываются два `input type=date`.
- Перед submit работает клиентская валидация.

## UI: kanban (`templates/kanban.html`)
### Что есть в интерфейсе
- Боковое выезжающее меню:
  - список исполнителей;
  - список систем.
- Для каждой выбранной группы строится доска со статус-колонками:
  - `Создано`, `Анализ`, `В очереди`, `В работе`, `В ожидании`, `Выполнено`, `Закрыто`.
- В заголовках:
  - сумма оценок по группе;
  - сумма по каждой статусной колонке.
- Карточки показывают номер, название, системы, дату, исполнителя, оценку, связи и метки.
- Описание задачи сворачивается/разворачивается через кнопку.
- Карточка подсвечивается (`task-highlight`), если `label_to_match` присутствует в `task.label`.

### Обнаруженные особенности шаблона
- В шаблоне есть дублирующийся блок рендера системных досок (вторая секция `{# Доски для систем #}` повторяет первую).
- В системной шапке выводится `{{ assignee }}`, хотя логичнее ожидать `{{ system }}`.
- Эти пункты не ломают идею приложения, но могут приводить к лишнему DOM/неверным заголовкам.

## Сильные стороны
- Простой и понятный пайплайн «форма → API → нормализация → канбан».
- Встроенные fallback-значения почти для всех нестабильных полей API.
- Удобная бизнес-сортировка исполнителей/систем/статусов.

## Технические риски
1. Глобальное состояние Flask (`tasks`, `label_to_match`) — риск гонок и «перетирания» между пользователями.
2. Много `except:` без конкретики — могут скрывать реальные ошибки интеграции.
3. `verify=False` и отключение предупреждений SSL — допустимо во внутреннем контуре, но небезопасно по умолчанию.
4. Потенциально off-by-one в пагинации: `totalPages` печатается как `+1`, а цикл идет `range(0, tasks_pages_count)`.
5. Дубли в `kanban.html` и возможная ошибка в выводе заголовка системной группы.

## Зависимости
Минимальные зависимости (`requirements.txt`):
